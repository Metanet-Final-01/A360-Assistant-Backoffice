# 부록 C. 만들었다가 되돌린 설계들

여기 있는 것들은 **아이디어만 들으면 그럴듯해서 다시 시도하기 쉽다.** 전부
실제로 구현하고 측정한 뒤 되돌린 것이니, 같은 길을 다시 가기 전에 이 문서를
먼저 읽을 것.

---

## 1. 메인 지표를 branch-aware로 교체 (2026-08-04, 기각)

### 무엇을 하려 했나

> "if 분기는 서로 배타적이라 하나만 실행된다. 그러니 분기 안의 액션은
> **대응되는 분기끼리만** 매칭을 인정하도록 메인 Action P/R/F1을 바꾸자."

구체적으로:
- if 밖 액션 → 기존대로 매칭
- if 안 액션 → 예측 분기가 대응된 정답 분기와 일치할 때만 인정
- 분기 대응은 새 알고리즘 없이 **이미 계산된 매칭 결과의 다수결로 역산**

실제로 구현해서 45개 샘플 전체에 돌렸다.

### 왜 기각했나 — 근거 4가지

**(1) 전제가 이 데이터에서 성립하지 않는다**

이 방식은 "예측에도 정답과 비슷한 분기 구조가 있다"를 전제한다. 실제로는:

| 에이전트 | 예측의 if 분기 개수 | 정답 |
|---|---|---|
| v2 | **9개 케이스 중 8개가 0개** | 6~15개 |
| v3 | 케이스당 1~3개 | 6~15개 |

**대응시킬 분기가 애초에 없다.**

**(2) 점수가 떨어지는 원인이 엉뚱하다**

| 그룹 | 기존 | branch-aware | 변화 |
|---|---:|---:|---|
| v1 | 0.328 | 0.195 | −41% |
| v2 (repro) | 0.233 | 0.191 | −18% |
| v3 (repro) | 0.367 | 0.256 | −30% |
| v3 (prior) | 0.462 | 0.330 | −29% |

떨어진 이유가 **"예측이 잘못된 분기에 매칭됐다"가 아니라 "예측에 if가 아예
없다"** 였다.

**최악 사례 — v3 / 0140**:

```
정답 액션 27개 중 분기 안에 있는 건 2개뿐
예측 액션 14개 중 분기 안에 있는 건 12개

기존:        TP 6,  F1 0.293
branch-aware: TP 0,  F1 0.000   <- 맞은 액션 6개가 전부 무효화
```

**액션은 제대로 만들었는데 if로 감쌌다는 이유만으로 0점**이 됐다. 이건
액션 선택 능력을 재는 지표로서 방어할 수 없다.

**(3) 고치려던 문제가 애초에 없었다**

이 설계의 동기는 **"분기가 3개면 같은 액션이 3번 중복 계산된다"** 였다.
그런데 확인해보니:

> `pair_rule_matches`는 **엄격한 1:1**이다. 예측 액션 하나는 `used_p` 집합으로
> 관리되어 **한 번만 소비된다.** 예측 액션 하나가 정답의 3개 분기에 3번
> 인정되는 일이 **구조적으로 불가능**하다.

**중복 카운트 버그는 존재하지 않았다.** 즉 이건 버그 수정이 아니라 순수하게
새 제약을 추가하는 것이었다.

**(4) 의도만 정확히 반영한 완화안은 사실상 아무것도 안 한다**

"양쪽 다 분기 안일 때만 대응을 검사"하는 좁은 버전도 만들어 돌려봤다.

→ **45개 샘플 중 1개만 바뀌었다** (v3/0098: 0.375 → 0.125). 예측에 분기가
없으니 검사할 게 없어서다.

### 단순성 기준에서도 최악이었다

| 방식 | 설명 |
|---|---|
| 현재 | *"같은 액션이면 매칭 → TP, 예측에만 있으면 FP, 정답에만 있으면 FN"* |
| branch-aware | *"예측 분기가 어느 정답 분기에 다수결로 대응되는지 역산하고, 대응된 분기 안에서만..."* |

초보자에게 설명이 안 된다.

### 결론

**분기 구조를 재현했는지는 이미 Branch Coverage / Branch Score가 정확히 그것만
재고 있다.** 메인 Action F1에 억지로 녹이면 **액션 선택 품질 신호가 구조 정렬
신호에 묻힌다.** 보조 지표로 두는 현재 구성이 맞다.

> ⚠️ Branch Score를 Action F1에 **더하거나 평균 내는 것**도 안 된다. 같은
> 액션이 두 번 반영된다.

## 2. 정답 액션 수(분모)에서 분기 중복 제거 (검토 후 기각)

### 무엇을 하려 했나

> "상호배타적 분기는 런타임에 하나만 실행되니까, 정답 액션을 셀 때 3개 분기를
> 다 세지 말고 하나로 치자. 그러면 Recall 분모가 줄어 점수가 오른다."

### 왜 기각했나

**봇이 3개 분기를 다 구현해야 모든 입력을 처리할 수 있다.**

```
정답: if (A) {...} elseIf (B) {...} else {...}
      -> 입력이 A든 B든 그 외든 처리 가능

예측: 한 분기만 구현
      -> 나머지 입력에서 동작 안 함. 실제로 기능이 빠진 것
```

1개만 구현한 예측은 **실제로 미완성**이다. 분모 3/9은 옳다.

점수가 오른다는 이유만으로 정당하지 않은 규칙을 넣지 않는다.

## 3. Gold 전용 UID 목록으로 핵심 액션 지정 (이전 세션에서 폐기)

### 무엇을 하려 했나

정답 워크플로우의 액션마다 `include: true/false`를 사람이 손으로 지정한
파일(`gold_core_actions/<id>.json`)을 만들어 채점에 쓰려 했다.

### 왜 기각했나

**정답에만 적용되는 비대칭 보정**이었다.

```
정답 액션 30개 -> 사람이 10개만 "핵심"으로 지정 -> 분모 10
예측 액션 20개 -> 그대로 20

=> 정답 분모만 줄어서 Recall이 부당하게 올라간다
```

**한쪽에만 적용하는 필터는 채점이 아니라 조작이다.**

### 대신 만든 것

지금의 **핵심업무 분류**(`classify_core_business_actions`)는 **정답과 예측
양쪽에 똑같이** 적용된다. 실제로 예측 쪽에서도 제외가 발생하는 것을 확인했다
(v3 기준 예측 19개 제외).

> `gold_core_actions/` 폴더는 아직 남아 있지만 **채점에 쓰이지 않는다.**
> 사람이 검토한 과거 참고자료이고, 새 분류기 결과를 이것과 대조해서 52/52
> 일치를 확인하는 **교차검증용**으로만 썼다.

## 4. 근거 없는 하드코딩 패키지 분류 (2026-07-30 삭제)

`core_task.py`와 `package_family()` / `salient_families()`가 "이 패키지는 핵심,
저건 아님"을 하드코딩하고 있었다.

**왜 지웠나**:
- `git log`로 확인해보니 이걸 도입한 커밋에 **근거가 전혀 없었다**
- 게다가 **자기모순**이었다 — File / Folder / XML / JSONHandler / Dictionary /
  List에 대한 분류가 서로 어긋났다

> 이 프로젝트가 다른 곳에 요구하는 것과 같은 수준의 근거 없이 "핵심 패키지"
> 분류를 다시 만들지 말 것.

## 5. LLM 판정 후보에 최소 유사도 컷오프 (제거됨)

Judge 매칭에서 "유사도가 0.3 미만이면 아예 물어보지 말자"는 임계값이 있었다.

**왜 뺐나**: 13개 골드셋 정도로만 대충 맞춘 잠정값이었고, **실제 검증 없이
매칭 게이트로 계속 쓰는 게 근거가 약하다**는 지적을 받았다.

**빼도 되는 이유**: "상호 Top-1"(서로가 서로를 1등으로 꼽음)이라는 조건 자체가
이미 강한 필터이고, 최종 판정은 어차피 LLM이 한다.

유사도 값은 `judge_log`에 계속 기록하므로, 나중에 실제 분포를 보고 **근거 있는
값**으로 다시 넣을 수 있다.

## 공통 교훈

이 다섯 가지에서 반복된 패턴:

1. **아이디어가 그럴듯하다고 맞는 건 아니다.** 다섯 개 모두 말로 들으면 합리적
   이었고, 실제 데이터에서 무너졌다.
2. **고치려는 문제가 진짜 있는지 먼저 확인한다.** 1번은 존재하지 않는 버그를
   고치려던 것이었다.
3. **점수가 오르는 방향이라고 정당한 건 아니다** (2번, 3번).
4. **임의의 숫자를 넣지 않는다** (5번).
5. **설명이 길어지면 그 규칙을 의심한다** (1번).
