## 이 숫자를 어떻게 읽나

### Precision은 높은데 Recall이 낮다

**"만든 것은 대체로 맞는데, 만들어야 할 것의 상당수를 안 만든다."**

- v3는 만든 액션의 57%가 정답과 일치한다 (Precision 0.571)
- 하지만 정답 액션의 34%만 만들어낸다 (Recall 0.342)

즉 **헛발질보다 누락이 문제**다. 에이전트가 워크플로우를 실제보다 짧게
만든다는 뜻이다.

### F1 0.4가 낮은 것 아닌가

**이 과제 기준으로는 낮지 않다.** 이유:

- 정답은 사람이 실무에서 만들어 Bot Store에 올린 **완성된 상용 봇**이다
- 에이전트는 **업무정의서 텍스트만 보고** 그걸 재현해야 한다
- 액션 하나만 달라도 틀린 것으로 센다 (부분 점수 없음)

비교 대상이 "정답률 90%가 정상인 분류 문제"가 아니라 **"사람이 만든 소프트웨어를
텍스트 명세만 보고 복원하기"** 다.

### v1 > v2 는 왜인가 (기대와 다름)

기대는 v1 < v2 < v3 였는데 **v1(0.328)이 v2 평균(0.279)보다 높게 나왔다.**

**점수를 기대 순서에 맞추는 보정은 하지 않았다.** 그대로 보고한다.

현재까지 아는 것:

- v2는 **실행 간 편차가 크다**. 두 번 돌린 결과가 0.233과 0.326으로 갈렸다
- v1의 단일 결과(0.328)는 **v2의 두 샘플 중 높은 쪽(0.326)과 거의 같다**
- 즉 **"v1이 v2보다 낫다"고 결론 내리기엔 표본이 부족하다**

⚠️ **v1은 1회밖에 안 돌렸다.** v1 자체의 편차를 모른다. 순서를 확정하려면 v1도
여러 번 돌려서 평균±분산으로 비교해야 한다.

## 알려진 한계 (전부 의도적으로 남긴 것)

### 1. v1 표본이 1개뿐

위에서 설명. **v1 < v2 < v3 순서는 아직 확정 아니다.**

### 2. 키워드 규칙의 부분문자열 매칭

`login`, `dialog`, `catalog`가 로그로 오분류될 수 있다. 현재 9개 케이스에서는
오탐 0건이라 그대로 뒀다. 상세 근거는 [05-validation.md](05-validation.md) 3번.

**골드셋 확장 시 반드시 점검할 것.**

### 3. CSS 셀렉터 클릭은 파라미터 비교가 안 된다

`#cc-main-conversion-block > div > ...` 같은 순수 CSS 셀렉터는 사람이 읽을 수
있는 텍스트가 없어서, 클릭 액션이 여러 개일 때 **등장 순서로만** 짝짓는다
(0131에서 실측 확인). 마땅한 해법이 없어 미해결로 남겼다.

### 4. 조건식 자체는 비교하지 않는다

`if (a > 5)` 와 `if (count > 5)` 가 논리적으로 같은지 판단하는 함수
(`judge_condition_equivalence`)가 코드에 있지만 **어디서도 호출하지 않는다.**
분기 안의 액션만 보고 조건식은 안 본다. 검토 끝에 "분기 커버리지 정도면
충분하다"로 결론 낸 의도적 선택이다.

### 5. 핵심업무 분류의 정확도는 9개로만 검증됐다

사람 검토본과 52/52 일치를 확인했지만 그건 **2개 케이스** 기준이다. 나머지
7개는 사람 대조 없이 LLM 판정을 신뢰한 상태다.

### 6. 분기 진단은 진단만 한다

Branch Coverage/Score는 메인 점수를 고치지 않는다. 이걸 메인 지표로 승격시키는
설계를 실제로 만들었다가 실측 후 되돌렸다 →
[appendix-c-rejected-designs.md](appendix-c-rejected-designs.md)
