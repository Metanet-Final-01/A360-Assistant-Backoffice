# 3. 전처리 — 채점 전에 무엇을 왜 걸러내나

## 왜 전처리가 필요한가

정답 워크플로우를 그대로 세면 이상한 일이 생긴다. 예를 들어 **0098(임시 파일
정리)** 의 정답은 액션이 **56개**인데, 이 중 **46개가 로그 폴더 만들기·감사
기록·오류 스냅샷 같은 준비 작업**이다. 실제 "정크 파일을 지운다"는 업무는
10개뿐이다.

이대로 채점하면 이런 문제가 생긴다.

- 어떤 봇이든 똑같이 들어가는 **로그 보일러플레이트가 점수를 지배**한다
- 에이전트가 업무를 완벽히 구현해도, 로그 준비를 안 했다는 이유로 Recall이
  10/56으로 떨어진다
- 봇들 간 **실력 차이가 안 드러난다** (다들 같은 보일러플레이트에서 점수를 얻거나 잃음)

그래서 채점 전에 **"이 업무를 구분 짓는 액션"만 남긴다.**

## 전처리는 3단계다

```
원본 goldset.json (정답 / 예측 양쪽 다)
   |
   [1단계] 무조건 빼는 것        <- 규칙만으로 판단, 논쟁 여지 없음
   |
   [2단계] 트리를 한 줄로 펼치기   <- if/loop 안의 액션을 꺼냄
   |
   [3단계] 핵심업무만 남기기      <- 애매한 것만 골라 LLM에게 물어봄
   |
   v
채점 대상 액션 목록
```

**세 단계 모두 정답과 예측에 똑같이 적용된다.** 한쪽에만 적용하면 그건 채점이
아니라 조작이다.

---

## [1단계] 무조건 빼는 것

`action_filters.py`가 담당한다. 판단이 필요 없는, 명백한 것만 뺀다.

| 빼는 것 | 이유 |
|---|---|
| **비활성화된 스텝** (`disabled: true`) | 실행되지 않는 코드다 |
| **주석 / 로그 기록 패키지** (`Comment`, `Logging`, `LogToFile`) | 업무 수행이 아니다 |
| **세션 열고 닫기** (`Browser.close`, `Email.connect/disconnect`) | 어느 봇에나 있는 준비/정리 동작 |
| **오류 처리(catch) 안의 액션** | 정상 흐름이 아니라 예외 상황 처리다 |
| **제어 구조 표식 자체** | `if`, `loop` 같은 건 액션이 아니라 껍데기다 |

> **일부러 좁게 잡았다.** MessageBox, 엑셀 서식, 경로 조합, 변수 대입은
> **빼지 않는다** — 업무의 일부일 수 있기 때문이다. 이건 3단계에서 따로 다룬다.

---

## [2단계] 트리를 한 줄로 펼치기

`if`와 `loop` 안에 들어있는 액션을 꺼내서 하나의 목록으로 만든다
(`flatten_scored_actions`).

**규칙은 단 세 줄이다.**

1. **분기(if/elseIf/else)는 전부 넣는다.** 정답이 3가지 경우를 3개 분기로
   처리한다면, 봇도 3가지를 다 만들어야 하기 때문이다. 하나만 만들면 나머지
   입력을 처리 못 하는 미완성 봇이다.
2. **반복(loop)은 본문을 1회만 넣는다.** 몇 번 도는지는 실행할 때 정해지므로
   정적인 워크플로우에서는 펼칠 수 없다.
3. **catch는 뺀다.** (1단계와 같은 이유)

### 여기서 나오는 흔한 오해

> "if의 3개 분기가 거의 같은 액션인데 다 세면 중복 아닌가?"

**아니다.** 매칭은 **1:1**이라 예측 액션 하나가 정답 3개에 3번 인정되는 일이
구조적으로 불가능하다([04-scoring.md](04-scoring.md) 참고). 정답 액션이 9개로
잡히는 건 실제로 9개를 다 만들어야 하기 때문이지, 중복 계산이 아니다.

이 오해 때문에 "분기별로 따로 채점하자"는 설계를 실제로 만들었다가 되돌린
적이 있다 — [appendix-c-rejected-designs.md](appendix-c-rejected-designs.md) 참고.

---

## [3단계] 핵심업무만 남기기 (가장 중요)

여기가 로그 보일러플레이트를 걸러내는 단계다.

### 문제: 같은 액션이 두 얼굴을 가진다

`Folder.createFolder`(폴더 만들기)를 보자.

- `folderPath=$pStrLogsFolder$` → **로그 폴더 준비**. 업무가 아니다.
- `folderPath=$pStrArchiveFolder$` → **보관 폴더 준비**. 업무 그 자체다.

**액션 이름만 봐서는 구분할 수 없다.** 파라미터를 봐야 안다.

### 해법: 3층 구조 (싼 것부터)

```
액션 하나
   |
   [층 1] 애매한 액션 목록에 없다?  -> 그냥 핵심업무로 인정하고 끝  (공짜)
   |
   [층 2] 파라미터에 log/audit/error/snapshot 있다? -> 로그로 보고 제외  (공짜)
   |
   [층 3] 남은 것만 LLM(gpt-4o-mini)에게 업무정의서 원문과 함께 물어봄  (유료)
```

**층 1 — 애매한 액션 목록** (`AMBIGUOUS_GENERIC_ACTIONS`)

이름만으로는 판단 못 하는 10종만 대상이다.

```
Folder.createFolder   Folder.deleteFolder   File.createFile
String.assign         Datetime.subtract     Datetime.toString
Datetime.assign       Number.assignToNumber Boolean.assign
MessageBox.messageBox
```

이 목록에 없는 액션(예: `Excel.writeDataTableToWorksheet`)은 **항상 핵심업무**로
본다. 범용 셋업으로 쓰인 사례를 실제로 본 적이 없기 때문이다.

**층 2 — 키워드 규칙** (무료)

파라미터 값에 `log`, `audit`, `error`, `snapshot`, `observability`가 있으면
로그성으로 판단한다. 9개 케이스에서 이 규칙에 걸린 74건을 **문맥까지 하나씩
전부 확인했고 오탐 0건**이었다.

**층 3 — LLM 판정** (유료, 남은 것만)

업무정의서 원문 + 실제 파라미터 값을 보여주고 "이 액션이 이 업무의 핵심인가"를
묻는다. 결과는 `case_id|액션이름|파라미터`를 키로 캐시해서 재실행 시 다시
호출하지 않는다.

> **주의**: LLM 프롬프트를 고치면 **반드시 캐시를 지워야 한다.**
> (`evaluation/gold_core_actions/_llm_classification_cache.json`)
> 안 지우면 옛날 판정이 계속 재사용된다.

### 실제로 잘 작동한다는 증거

0098의 `Folder.deleteFolder` 5개가 이렇게 갈렸다.

| 파라미터 | 판정 |
|---|---|
| `folderPath=$pStrLogsFolder$/*` | ❌ 제외 (로그 정리) |
| `folderPath=$pStrPercentTemp$\...` | ✅ 핵심업무 |
| `folderPath=$pStrRecent$\...` | ✅ 핵심업무 |
| `folderPath=$pStrWPrefetch$\...` | ✅ 핵심업무 |
| `folderPath=$pStrWTemp$\...` | ✅ 핵심업무 |

**같은 액션 이름인데 목적으로 정확히 갈랐다.** 라벨 단위로 일괄 필터링하는
방식이었다면 5개가 전부 빠지거나 전부 남았을 것이다.

### 전처리 후 실제 숫자 (v3 기준)

| 케이스 | 정답 제외 | 정답 남음 | 예측 제외 | 예측 남음 |
|---|---:|---:|---:|---:|
| 0085 | 25 | 17 | 4 | 5 |
| 0089 | 24 | 6 | 8 | 3 |
| 0098 | 46 | 10 | 3 | 6 |
| 0131 | 13 | 24 | 0 | 19 |
| 0140 | 11 | 27 | 1 | 14 |
| **합계** | **168** | | **19** | |

정답에서 훨씬 많이 빠진다. **규칙은 양쪽에 똑같이 적용되고, 데이터가 다를
뿐이다** — 정답에는 로그 보일러플레이트가 많고 예측에는 거의 없어서다.

그리고 이 방향은 **에이전트에게 유리하다.** 정답의 로그 액션 168개를 빼주지
않았다면 그건 전부 "에이전트가 못 만든 것(FN)"으로 잡혀 Recall이 훨씬 낮아진다.

## 자주 나오는 질문

**Q. 업무정의서 Task 1이 "로그 구성"이라고 써 있는데, 그럼 로그도 업무 아닌가?**

맞다. 업무정의서에 있는 내용이다. 하지만 **모든 봇에 똑같이 들어가는
보일러플레이트**라, 포함하면 모두의 점수가 똑같이 오르내릴 뿐 **봇 간 실력
차이를 구분하지 못한다.** 양쪽에서 대칭으로 빼서 "업무를 구분 짓는 부분"에
집중한다.

**Q. 키워드 규칙이 `login`도 로그로 착각하지 않나?**

**할 수 있다.** 부분문자열 매칭이라 `login`, `logout`, `dialog`, `catalog`가
걸린다. 현재 9개 케이스에서는 오탐이 0건이라 그대로 뒀다. 이걸 왜 안 고쳤는지와
언제 고쳐야 하는지는 [05-validation.md](05-validation.md)에 있다.
