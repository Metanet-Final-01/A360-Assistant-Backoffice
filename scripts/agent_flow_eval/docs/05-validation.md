# 5. 이 규칙들이 타당한지 어떻게 확인했나

규칙을 정하는 것과 그 규칙이 맞다는 것은 다르다. 이 문서는 **각 규칙을 실제로
어떻게 검증했는지**를 적는다. 전부 실제로 돌려본 결과이고, 재현 방법도 같이
적었다.

## 검증 원칙

> **"합리적으로 보인다"는 근거가 아니다. 실제 데이터에서 확인해야 근거다.**

그래서 아래 항목마다 **무엇을 어떻게 확인했고, 결과가 무엇이었는지**를 적었다.
확인 결과 **내 예상이 틀린 경우도 그대로 적었다.**

---

## 1. 재현성 — "Rule-only는 항상 같은 값이 나오는가"

**왜 확인해야 했나**: Rule-only를 "공식 기준선"이라고 부르려면 누가 언제
돌려도 같은 숫자가 나와야 한다. 그런데 짝짓기 코드가 파이썬 `set`을 순회하는데,
파이썬은 **실행할 때마다 문자열 해시를 무작위로 바꾼다.** 순회 순서가 달라지면
결과도 달라질 수 있다.

**어떻게 확인했나**: 해시 시드를 강제로 바꿔가며 3번 돌렸다.

```bash
PYTHONHASHSEED=0     python3 ...   # 9개 케이스 TP와 Chain F1 출력
PYTHONHASHSEED=1     python3 ...
PYTHONHASHSEED=12345 python3 ...
```

**결과**: 9개 케이스 전부 **TP도 Chain F1도 완전히 동일**했다.

```
0085:0.3636  0089:0.2222  0098:0.2500  0112:0.7000  0131:0.2791 ...   (3회 모두 같음)
```

**왜 안전한가**: 짝짓기가 **액션 이름별로 독립**이라, 어떤 이름을 먼저 처리하든
각 이름 안에서의 결과가 바뀌지 않는다.

✅ **"LLM 없이 재현 가능한 기준선"은 실제로 성립한다.**

---

## 2. 핵심업무 분류 — "라벨이 아니라 목적으로 가르는가"

**왜 확인해야 했나**: 만약 이 분류가 `Folder.deleteFolder`를 통째로 빼거나
통째로 남긴다면, 그건 "목적 판단"이 아니라 그냥 라벨 필터링이다.

**어떻게 확인했나**: 0098에서 같은 액션 이름의 인스턴스별 판정을 꺼내봤다.

**결과**:

| 파라미터 | 판정 |
|---|---|
| `folderPath=$pStrLogsFolder$/*` | ❌ 제외 (로그 정리) |
| `folderPath=$pStrPercentTemp$\...` | ✅ 핵심업무 |
| `folderPath=$pStrRecent$\...` | ✅ 핵심업무 |
| `folderPath=$pStrWPrefetch$\...` | ✅ 핵심업무 |
| `folderPath=$pStrWTemp$\...` | ✅ 핵심업무 |

✅ **같은 이름 5개를 목적으로 정확히 갈랐다.**

**추가 근거**: 사람이 직접 검토해둔 파일(`gold_core_actions/0089.json`,
`0098.json`)과 대조해서 **52/52 전부 일치**하는 것도 확인했다.

---

## 3. 키워드 규칙 — "로그가 아닌 걸 로그라고 하지 않는가"

**왜 확인해야 했나**: 이 규칙은 **LLM 앞단에서 무료로 걸러내는 단계**라,
잘못 걸리면 LLM에게 물어보지도 않고 조용히 제외된다.

**어떻게 확인했나**: 9개 케이스에서 이 규칙에 걸린 정답 액션 **74건 전부**를
매칭된 키워드 주변 문맥까지 출력해서 하나씩 눈으로 봤다.

**결과**: **오탐 0건.** 전부 진짜였다.

```
[0085] String.assign        kw=Log    ...sourceString=$pStrLogsDateFolder$\AuditLog...
[0085] Folder.createFolder  kw=Error  ...folderPath=$pStrErrorLogFolder$...
[0131] Folder.createFolder  kw=Snapshot ...folderPath=$sSnapshotsFolder$...
                                    ... (74건 전부 확인)
```

### 여기서 내 예상이 틀렸던 것

0089(파일 보관)와 0098(정크 삭제)에서
`Datetime.subtract(val=$pNumLoggingPeriod$, unit=DAYS)`가 제외된 걸 보고
**"이 두 봇의 핵심업무가 바로 'N일 지난 파일 처리'인데, 변수명에 Log가
들어갔다는 이유로 잘못 뺀 것 아닌가?"** 하고 의심했다.

**확인 방법**: 두 업무정의서 원문을 직접 열어봤다.

**결과**: **내 의심이 틀렸다.** 두 정의서 모두 Task 1이 명시적으로
`"실행 준비 (로그 구성)"` 이고 그 안에 `"보관 기간이 지난 이전 로그 폴더는
삭제한다"` 가 있다. 즉 `LoggingPeriod`는 **로그 보관주기**가 맞다. 실제
업무(파일 보관 / 정크 삭제)는 날짜 임계값을 아예 쓰지 않는다.

✅ **제외가 정확했다.**

### 알려진 한계 (안 고치기로 한 것)

이 규칙은 **부분문자열 매칭**이라 원리상 이런 게 걸린다.

```
login page      -> "log" 걸림  ❌ 잘못됨
dialog box      -> "log" 걸림  ❌ 잘못됨
catalog number  -> "log" 걸림  ❌ 잘못됨
terror          -> "error" 걸림 ❌ 잘못됨
```

**왜 지금 안 고쳤나:**

1. 현재 9개 케이스에서 **오탐 0건**이다
2. 대안으로 "단어 단위로 쪼개서 비교"를 실제로 만들어 돌려봤더니,
   `$sRunlogpath$`처럼 **전부 소문자로 붙은 변수명을 놓쳐서 지금보다
   부정확**해졌다. 그걸 메우려면 예외 목록이 붙어 복잡해진다
3. 아직 일어나지 않은 문제를 위해 코드를 미리 복잡하게 만들지 않는다

⚠️ **골드셋을 9개 밖으로 넓히면 이게 실제로 터질 수 있다** (RPA 봇에서 `login`은
흔한 핵심업무다). 확장할 때는 위 74건 확인과 같은 방식으로 제외 사유를 한 번
훑어볼 것.

## 4. 동치 규칙 — "다른 작업을 같다고 묶지 않았는가"

**왜 확인해야 했나**: 동치 규칙은 TP를 직접 늘린다. 근거 없이 묶으면 점수가
부당하게 올라간다.

**어떻게 확인했나**: 45개 그룹 중 **패키지를 넘나드는 그룹 전부**를 출력해서
직접 봤다. (같은 패키지 안의 별칭은 위험도가 낮다)

**결과**: 전부 **"같은 작업을 다른 패키지로 구현한 것"** 이었다.

```
[교차패키지] Email.cloudUsingSendAction
     Email.sendMail
     Gmail.Send
     Microsoft 365 Outlook.ms365OutlookSend      <- 전부 "메일 보내기"
```

✅ **다른 작업을 억지로 묶은 건 없다.**

**반대 사례도 있다**: `Excel_MS.CreateSpreadsheet`(새 파일 생성)와
`Excel_MS.OpenSpreadsheet`(기존 파일 열기)는 **동치로 넣지 않았다.** 실제
데이터를 확인해보니 예측 쪽 `OpenSpreadsheet`는 `filePath: null`인 미완성
구현이었다. 비슷해 보인다고 넣지 않았다.

## 5. WorFBench 변환기 — "분기를 잃지 않는가"

**왜 확인해야 했나**: 채점에 쓰이는 변환 함수 이름이 `_canonical_path`
("대표 경로 하나로 접는다")였다. 이름대로라면 정답 액션이 사라진다.

**어떻게 확인했나**: 변환 결과 액션 수를 우리 메인 파이프라인과 비교했다.

**결과**: 9개 케이스 **전부 정확히 일치** — 즉 **아무것도 접지 않고 있었다.**

```
case    WorFBench노드    우리(필터 전)
0085         42              42
0098         56              56
0419         47              47      ... 9/9 일치
```

**이름이 거짓말이었다.** 반면 별도 스크립트
`processing/convert_to_worfbench.py`는 **진짜로 접고 있었고**, 그래서 액션을
잃고 있었다(0376은 20개 중 6개, 0098은 4개).

✅ **2026-08-04에 둘을 `flatten_all_branches`로 통일했다** — 이름도 동작대로
바꾸고, 규칙도 "분기는 전부 넣는다"로 맞췄다. 별도 스크립트의 출력물은 어떤
채점기도 입력으로 쓰지 않아서(채점은 goldset.json을 직접 읽는다) **점수 변화는
0이었고**, 9개 v3 WorFBench 점수를 재계산해서 이전 발표값과 전부 일치함을
확인했다.

---

## 6. Chain 계산 — "LIS 구현이 맞는가"

**어떻게 확인했나**: 같은 짝 위에서 **LCS(최장 공통 부분수열)** 로도 계산해서
LIS 결과와 같은지 단위 테스트로 비교한다.

**왜 이게 검증이 되나**: 짝이 이미 1:1로 확정된 상태에서는 두 방법이
**수학적으로 같은 값**을 내야 한다. 다르면 짝짓기 로직에 버그가 있다는 뜻이다.

✅ 실제로 이 테스트가 **버그를 잡은 적이 있다** — 같은 워크플로우가 여러 곳에
inline되어 같은 uid가 중복 등장하면서 위치 계산이 어긋난 문제였다. 그래서 지금은
액션마다 `uid#등장순번`으로 유일한 id를 만든다.

---

## 7. 전체 회귀 — "고치고 나서 안 깨졌는가"

변경할 때마다 두 가지를 돌린다.

1. **단위 테스트 26개** (`pytest`)
2. **저장된 v2/v3 예측으로 재채점** 후 이전 점수와 대조

예: gold 파일명을 바꾸고 채점기 경로를 통합했을 때, 18개 행 전부
**점수가 완전히 동일**함을 확인하고 나서 반영했다.
