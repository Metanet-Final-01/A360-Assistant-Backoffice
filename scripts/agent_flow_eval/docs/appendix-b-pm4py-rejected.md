# 부록 B. PM4Py — 도입하려다 완전히 폐기한 근거

## PM4Py가 뭔가

**프로세스 마이닝** 라이브러리다. 원래 용도는 이렇다.

> 회사에 "주문 처리 절차는 이래야 한다"는 **표준 프로세스 모델**이 있고,
> 실제 시스템 로그에 **수천 건의 실행 기록**이 쌓여 있다.
> → 실제 실행이 표준을 얼마나 지켰는지(**적합도, fitness**) 측정한다.

워크플로우를 다루는 도구니까 우리 과제에도 맞을 것 같아서 도입을 시도했다.

## 무엇을 해봤나

정답 워크플로우를 Petri net(`.pnml`) / process tree(`.ptml`)로 변환하고,
에이전트 예측을 "실행 로그"로 취급해서 PM4Py의 적합도 검사를 돌렸다.

## 결과: 실측에서 완전히 무의미했다

**금 시세 조회 봇**으로 실제 테스트했다 (정답 vs `gpt-5.6-luna` 예측).

```
fitness   0.089
precision 0.000
```

**정상적으로 작동하는 예측인데 점수가 0에 가까웠다.**

## 왜 그런가 — 도구를 잘못 쓴 것

문제는 PM4Py가 아니라 **우리 과제의 성격**이었다.

| | PM4Py가 전제하는 상황 | 우리 상황 |
|---|---|---|
| 비교 대상 | **하나의 정해진 표준** vs 실행 기록 | **사람의 구현 하나** vs **에이전트의 다른 구현** |
| 다른 것의 의미 | **일탈(deviation)** — 문제 | **정상적인 구현 차이** — 문제 아님 |
| 로그 개수 | 수천 건 | **1건** |

RPA 워크플로우는 **같은 업무를 여러 방법으로 구현할 수 있다.**

```
정답:  Recorder.capture (화면 녹화 방식으로 클릭)
예측:  WebAutomation.clickelement (요소를 직접 클릭)
       -> 둘 다 "클릭"이고 둘 다 맞다
```

PM4Py는 이걸 **전부 일탈로 잡는다.** 표준에서 벗어났으니까. 그래서 정상적인
구현 차이까지 몽땅 감점되어 점수가 바닥을 쳤다.

**즉, 적합도 검사 도구를 "정답 채점"에 쓴 게 잘못이었다.** 이건 도구의 결함이
아니라 용도 오적용이다.

## 우리가 대신 만든 것

PM4Py가 못 한 걸 해결하려면 **"다른 이름인데 같은 일"을 인정할 수 있어야
한다.** 그래서 이렇게 바꿨다.

| PM4Py 방식 | 우리 방식 |
|---|---|
| 표준에서 벗어나면 일탈 | **동치 규칙**으로 같은 작업의 다른 구현을 인정 ([04-scoring.md](04-scoring.md)) |
| 전부 자동 판정 | 규칙으로 안 되는 것만 **LLM에게 물어봄** |
| 적합도 하나 | **Precision / Recall / F1** 로 분리 — 누락과 헛발질을 구분해서 봄 |

## 지금 상태

**코드에는 PM4Py가 없다.** 문서와 주석의 역사적 언급만 남아 있다.

⚠️ **되살리지 말 것.** 위 실측 근거를 다시 확인하지 않고 "워크플로우 평가에
프로세스 마이닝을 쓰면 좋겠다"는 아이디어만으로 재도입하면 같은 실패를
반복한다.

## 이 실패에서 배운 것

> **도구가 다루는 대상이 같다고 목적까지 같은 건 아니다.**

PM4Py도 워크플로우를 다루고 우리도 워크플로우를 다루지만, PM4Py는
**"규정을 지켰나"** 를 묻고 우리는 **"같은 일을 해냈나"** 를 묻는다. 이 차이를
실측 전에는 알아채지 못했다.

그래서 이 프로젝트는 지표를 도입할 때 **실제 데이터로 먼저 돌려보고**
숫자가 말이 되는지 확인한 뒤에 채택한다.
