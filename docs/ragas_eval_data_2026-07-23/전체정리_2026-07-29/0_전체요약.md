*이 프로젝트 전체를 처음부터 다시 파악할 수 있도록 정리한 문서. 목표: A360 RAG 파이프라인의 chunk_size, overlap, 검색 방식(vector/BM25/hybrid/reranker) 하이퍼파라미터를 실측 근거로 확정.*

## 1. 최종 확정값 (지금 시점 결론)

| 항목 | 확정값 | 근거 |
|---|---|---|
| chunk 방식 | char 기준 | char vs token 성능 차이 없음(115+ 검정 전부 불유의), char가 더 단순 |
| chunk_size | **1200자** | EDA 포화점, gold 경계보존율 98.3%, cs1500/1800 테스트해도 추가 이득 없음 |
| overlap | **10%** | 경계복구율 EDA(10%에서 이미 100% 복구), 0/10/20/30% 전부 pairwise 유의차 없음, 20%/30%는 비용만 증가 |
| 검색 방식 | BM25 + Vector | Vector-only 대비 압도적 개선(gpt-4o-mini·로컬 EXAONE 둘 다 확인) |
| 결합 방식 | 정규화 융합(min-max+arithmetic_mean), w_bm25=0.5/w_vector=0.5 | 16개 fusion 설정 실제 Context P/R 재채점 1위, RRF(k=60, 현 프로덕션 기본값) 대비 개선 |
| candidate pool | 100 | 포화점 확인(100 이후 129건 기준 증가폭 1건 이하) |
| reranker | Voyage rerank-2.5-lite, 후보 50개 | 20→50 개선, 50→100은 결과 완전 동일(비용만 증가) |
| final top-k | 5 | |

## 3. Chunk size 확정 과정

### 3-1. 후보 스크리닝 (char 5개: 300/600/900/1200/1500, token 9개: 150/250/512/900/1000/1024/1200/1500/2048)

- 로컬 EXAONE으로 vector-only 129건 전체 평가
- **핵심 트레이드오프 발견**: 작은 청크 → Hit@1/MRR 유리(정답을 정확히 상위로 뽑음), 큰 청크 → EvidenceCoverage/ContextRecall 유리(근거를 충분히 담음). 두 방향이 반대인데, **실제 생성 품질(Faithfulness 등)은 EvidenceCoverage 쪽 경향을 따라감** → 이게 큰 청크를 선택한 실질적 이유
- EDA로 다음을 확인(전부 `EDA_그래프/`에 시각화):
  - 문서유형별 원문 길이 차이(doc_page만 원래 길다, action_schema/package_overview는 원래 짧음 → chunk_size 영향이 문서유형마다 다름)
  - chunk_size 커질수록 "1청크 문서 비율" 완만히 포화(1200~1500 부근에서 60~70%대)
  - gold 근거 스니펫이 청크 하나에 온전히 담기는 비율: cs1200에서 98.3%, cs1500 99.4%, 이하로 갈수록 뚜렷이 하락
  - 실제 청크 길이의 변동폭(IQR)이 chunk_size 커질수록 평균보다 훨씬 크게 벌어짐(cs300→cs1500 평균 3.4배, IQR 7.8배 / token은 더 심해서 7배/25배)

### 3-2. cs1500 이후 추가 검증: cs1800

- 다른 컴퓨터에서 DB 덤프(`cs1800_ov0`)를 받아와 복원 후 vector-only 129건 평가
- **결과: 더 안 좋아지거나 정체** — EvidenceCoverage만 미미하게 상승(+1.9%p, 계속 둔화 중인 추세 연장), Hit@1은 6개 후보 중 최저. "1200~1500이 포화점"이라는 결론을 1800까지 확장 검증.

### 3-3. char vs token, 그리고 "2ⁿ" 가설

- 실제 크기 매칭쌍(cs1200↔tok900, cs1500↔tok1024, cs300↔tok250, cs600↔tok512)으로 paired 유의성검정(Wilcoxon+bootstrap+McNemar) — **vector-only 25개 + hybrid+rerank 59개 + McNemar 31개 = 115개 검정 중 유의 0건**
- "2ⁿ이 유리하다"는 가설(tok1000 vs tok1024, tok500 vs tok512)도 **20개 검정 전부 불유의** — 2ⁿ은 하드웨어 얘기지 답변 품질과 무관하다는 결론
- 핵심 원리: 이 코퍼스는 글자당 토큰 비율이 거의 일정(1.4자/토큰)해서, char로 세든 token으로 세든 실제로 자르는 위치가 거의 같음 → "어떻게 셌나"가 아니라 "실제로 얼마나 잘렸나"만 성능에 영향

### 3-4. 알게 된 데이터 이슈

- `cs600_ov60`, (구)`tok500_ov0`, (구)`tok600_ov0` 테이블이 실제로는 비어있었음(0건) — 나중에 새 덤프로 해결(`tok500_ov0` 2026-07-27, 14,275건 정상 복원)
- cs300/cs1500 두 후보에서 93건 결측 발견 → 원인 규명: 스냅샷 타이밍 차이(문서가 2026-07-16에 추가됨, 이 두 후보는 그 이전에 빌드됨), 버그 아님, 골드셋 영향 1/129건뿐

## 4. Overlap 확정 과정

### 4-1. gpt-4o-mini 스윕 (0/10/20%, char 4개 크기: 300/900/1200/1500)

- **전 크기대에서 동일 패턴**: 0%→10% 개선, 10%→20%는 추가 개선 없거나 하락

### 4-2. 로컬 EXAONE으로 재확인 + 심화 EDA

- cs1200_ov0 vs cs1200_ov120(10%): hybrid+rerank 적용 후에도 유의차 없음(=10%가 손해 없음을 재확인)
- **경계복구율 분석**(이 프로젝트에서 새로 발굴한 핵심 지표): 129건 골드셋 179개 gold snippet 중 0%에서 실제로 청크 경계에 걸려 깨진 것만 추려서 overlap별 복구율 계산 → **cs1200/1500은 10%에서 이미 100% 복구, 20%는 추가 복구 0건**
- **중복 비용 분석**: overlap은 청크 "길이"가 아니라 "개수"만 늘림(boxplot으로 확인) — 20%는 10%보다 중복 데이터가 약 2배 이상(+11.8~15.8% vs +4.9~6.4%)

### 4-3. 20%, 30%까지 실제로 돌려본 결과 (2026-07-28~29)

- `cs1200_ov240`(20%), `cs1200_ov360`(30%) 덤프를 받아와 복원 → 신 확정 파이프라인(정규화 융합)으로 실제 129건 평가
- **결과**: 0%→10%→20%→30%로 갈수록 숫자는 미세하게 계속 오르는 것처럼 보임(특히 ContextRecall이 30%에서 1.0000) — 하지만 **10% vs 20%, 10% vs 30% 둘 다 paired 유의성검정 0/10, 심지어 30%가 20%보다도 신호가 더 약함**(raw p-value가 더 큼) → "overlap을 계속 늘리면 계속 좋아진다"는 패턴이 아님, 노이즈 범위
- 재현성 확인: cs1200_ov120(10%) 3회 반복 — 거의 완벽 재현(노이즈 <0.003), cs1200_ov240(20%) 3회 반복(RRF 방식) — 노이즈 <0.008. **로컬 EXAONE 생성+채점은 temperature=0이라 사실상 결정론적**이고, 유일하게 미세한 비결정성은 Voyage reranker(외부 API) 쪽에서 나옴
- **결론: 10% overlap 유지** — 20%/30%가 숫자상 미세하게 좋아 보일 때도 있지만 증명 안 되고, 메커니즘 근거(경계복구 이미 포화)도 없고, 비용만 계속 늘어남

## 5. 검색 방식(Vector/BM25/Hybrid/Reranker) 확정 과정

### 5-1. gpt-4o-mini 단계별 비교 (2026-07-21, 나중에 발굴한 자료)

Vector→BM25→Hybrid→Hybrid+Rerank 4단계 순차 비교(cs1200 기준):

| 방식 | doc_page(cs1200_ov0) | action_schema(cs1200_ov120) |
|---|---|---|
| Vector | 0.783 | 0.923 |
| BM25 | 0.816 | 0.874 |
| Hybrid | 0.871 | 0.949 |
| **Hybrid+Rerank** | **0.962** | **0.991** |

- doc_page는 BM25 단독이 Vector보다 나음(자연어 설명 위주라 키워드 매칭 유리), action_schema는 반대(의미 유사도가 더 잘 맞음) — **문서유형마다 유리한 검색방식이 다르다는 게 왜 Hybrid가 필요한지의 핵심 근거**

### 5-2. 로컬 EXAONE으로 재확인 (2026-07-26)

- tok1024 기준 vector-only vs hybrid+rerank: Hit@1 33%→69%(2배), MRR 0.44→0.79, ContextPrecision 0.74→0.95 — gpt-4o-mini 결론이 로컬 모델로도 그대로 재현됨

### 5-3. hybrid 하이퍼파라미터 단계적 탐색 (2026-07-26~27)

GPT 제안대로 전수교차 대신 단계적으로 진행:

1. **branch candidate pool 포화점**: 10~200 테스트 → 100 근방부터 증가폭 129건 기준 1건 이하로 포화
2. **fusion 방식 비교**(RRF 5종 vs 정규화 융합 3종, pool 100/150): 처음엔 **자체 evidence_coverage/MRR 지표(proxy)로 스크리닝** — 정규화 융합이 우세해 보였고, 그중 w_bm25=0.7/w_vector=0.3("ranking형")이 최고로 나옴
3. **Pareto 선정**: ranking형(0.7/0.3) + coverage형(0.5/0.5) 2개로 압축
4. **reranker_pool × top_k**: pool 10/20/50/100 교차 → pool=50이면 충분(100은 비용만 증가)
5. **실제 생성+RAGAS 평가**: anchor(RRF) vs ranking형 vs coverage형, tok1024 기준 129건 전체 실행

### 5-4. 중대한 방법론 이슈 발견 및 수정 (2026-07-26~27)

- **문제**: 1~4단계 스크리닝이 진짜 목표지표(RAGAS Context Precision/Recall)가 아니라 대리지표(evidence_coverage, MRR/Hit@1)로 이루어졌다는 지적을 받음
- **검증**: Context Precision/Recall(WithReference 버전)은 생성 없이도 채점 가능하다는 걸 확인 → 16개 fusion 설정 전체를 실제 지표로 재채점(로컬 서버 GPU 드라이버 장애로 한 차례 중단됐다가 복구 후 재실행, 총 15시간)
- **결과**: proxy 지표로 뽑았던 "ranking형(0.7/0.3)"이 실제 지표로는 **16개 중 꼴찌**(HM 0.8575)로 확인, 반대로 "coverage형(0.5/0.5)"이 **실제로도 1위**(HM 0.8923, pool=150 기준)로 확인 — proxy가 잘못된 신호를 준 구체적 사례로 기록됨
- 다행히 coverage형은 이미 5단계 실제 생성 평가까지 완료해뒀던 것이라 그대로 최종 채택 근거로 사용 가능했음
- **추가로 발견한 모순**: 이후 실제 생성+rerank까지 포함한 전체 파이프라인 재비교에서는 ranking형(0.7/0.3)이 오히려 coverage형보다 높게 나오는 경우도 있었음(HM 0.9707 vs 0.9610) — **fusion 단독(rerank 전) 품질과 rerank 이후 최종 품질이 반드시 일치하지 않는다**는 것을 시사. 다만 anchor/ranking형/coverage형 셋 다 유의성검정에서 0/28로 유의차 없어서, 이 순위 변동도 노이즈 범위 안일 가능성이 높음 — **핵심 결론(정규화 융합이 RRF보다 방향성 있게 낫다, w=0.5/0.5가 합리적 선택)은 유지되지만 "16위였다"는 표현은 fusion-only(rerank 전) 기준이라는 단서가 필요**

### 5-5. RRF-k 특성 확인

- 실제 재채점 데이터에서 RRF k=10, k=20이 가장 좋음(HM 0.886~0.887), **현재 프로덕션 기본값 k=60은 중위권**(0.881~0.884), k=1은 확실히 나쁨 — 그래도 RRF 최고값(0.887)조차 정규화 융합 1위(0.892)보다 낮음

## 6. 재현성(Reproducibility) 검증

- 로컬 EXAONE 생성+채점은 temperature=0으로 고정 → **사실상 결정론적**, 3회 반복 시 대부분 지표 완전 동일, faithfulness/answer_correctness만 0.001~0.005 수준 미세 노이즈(GPU 부동소수점 연산 순서 비결정성 추정)
- **유일하게 완전한 결정론이 아닌 부분: Voyage reranker(외부 API)** — hit@3/MRR에서 아주 작은 변동(최대 0.0078) 관측
- "AI가 채점해서 반복이 중요하다"는 우려는 이 설정(temperature=0)에서는 크게 기우였음이 확인됨 — 후보 간 관측된 몇 %p 차이는 재현성 노이즈로는 설명 안 되고 진짜 표본 변동(질문별 난이도)에서 옴
